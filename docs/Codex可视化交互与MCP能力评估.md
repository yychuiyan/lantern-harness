# Lantern 可视化交互与 Codex MCP 能力评估

评估日期：2026-11-26。评估基线：`package.json` 0.2.16、HEAD `ae84f8b`；实施结果随 `0.2.17` 发布。

## 1. 结论

**不建议把 Lantern 全部功能都改成弹窗。优先考虑 2 项，另外 5 项按实际使用需求决定；其余保持现有 MCP 或先补正式 MCP。**

本次逐项对照了 **31 个扩展插件**、补齐 W1–W3 后源码实际注册的 **135 个 Lantern MCP 工具**，并按能力族检查会话/全局目录。内置目录有 26 个会话条目、110 个全局条目，存在跨目录重叠，不能当作 136 项独立且全部已落地的产品功能。

- **W1 已补齐：场景遗漏补全与用例修订审阅。** 已增加预览、文件哈希 / 草稿 revision、成功写回后标记和逐项回执；不再以“跳转工作台”代替保存。
- **W2 已补齐：测试报告的材料选择与结果审阅。** 已增加真实用例 / 统计上下文、缺口、草稿校验和原子保存；报告库可直接打开整理抽屉。
- **W3 已补齐：Lantern 记忆建议审阅。** 已增加批量选择、重复提示、revision 校验和逐项采纳 / 拒绝回执；只处理 Lantern 自有队列。
- **条件候选 W4–W7：** 复杂工作汇报选材、技能/模板批量变更预览、项目管理批量关系调整、年度计划/OKR 草案。仍按实际需求决定。
- **不重复建设：** 需求分析、用户故事审查、测试点、XMind、业务地图、自动化项目/脚本/运行、缺陷提交、通用测试统计、现有用例执行和质量评审报告等，已有可组合使用的 MCP 主链路。
- **先补 MCP 即可：** 知识库生成与检索、待办/任务普通操作、本地项目管理 CRUD、人工用例执行统计维护等。没有同名 MCP 工具，不代表必须做图形窗口。

用例生成浏览器窗口是参照实现，**不计入待建设候选**。本轮随后补齐 W1–W3 的服务、页面和 MCP；评估部分本身不写业务资产。

## 2. 判断标准与证据边界

本次的“这样做”指：**Codex 发起 → Lantern 展示可视化选择/预览 → 用户明确确认 → Codex 读取确认结果 → 继续调用正式执行/保存工具。**

| 分类               | 判定                                                                        | 处理方式                            |
| ------------------ | --------------------------------------------------------------------------- | ----------------------------------- |
| MCP 已能闭环       | 可通过已有工具取得真实上下文、执行/保存并回读结果；人工确认也可在聊天中完成 | 排除，不因为选项多就重新做窗口      |
| 只缺 MCP 接口      | 数据与规则已有，参数少、可用自然语言明确表达                                | 优先补领域 MCP，不强制窗口          |
| 确实需要图形审阅   | 多项关联选择、逐条采纳、差异预览、关系变动影响难用一两句确认                | 列为窗口候选；同时补齐正式服务边界  |
| 纯查看或主机配置   | 仪表盘、布局、模型/密钥设置、浏览器登录等已有适合的页面                     | 保留既有页面，必要时打开入口        |
| Codex 自己已有能力 | 编码、文件搜索、终端、压缩上下文、子代理、常规联网、通用产物生成            | 不迁移 Lantern 内部运行时来重复实现 |

“HTTP 接口存在”“Lantern 内部模型有工具”“Codex 能用 shell 修改 JSON”都不等于对外 MCP 已覆盖。尤其不能用直接改业务 JSON 代替领域校验、revision 与回执。

评估证据是当前源码、注册清单、页面回调与保存路径。**这不是全部功能的运行验收**，也没有确认每个插件在当前空间都已开启。用例配置窗口的渲染、来源互斥及测试确认回传在此前开发中实测过；不把这一项的结果扩展为全平台验证。

### W1（已完成）：场景遗漏补全与用例修订审阅

**为什么优先：** 测试资产直接受益，而且已有可复用的 `CaseReviewDrawer`、`CaseBlindspotPanel`、真实表头读取与评审记录服务。

原缺口（已修复）：

1. `lantern_case_review_context` 读取的是质量评审技能；`lantern_case_review_save` 只发送 `review`，不会修改用例正文，也没有暴露 `blindspot`。
2. UI 目前探测盲区、勾选补全后，跳转绑定的 Lantern 工作台，让模型按原文件的需求分组写回。
3. `CaseReviewDrawer` 的 `onWriteback` 在跳转前就把所选条目标为 `added: true`。源码层面可见“状态先完成、资产后写入”的一致性风险；本次未对该失败场景做运行复现。
4. 服务端确实还保留旧 `/__tb_casereview/append`，不是完全没有追加能力；但当前主 UI 不走它，且该分支未像报告保存一样强制校验原文件哈希。不能简单给旧接口套一个 MCP 就宣称闭环完成。

建议流程：读取原文件与需求基线 → Codex 生成候选 → 页面勾选并预览行级差异 → 用户确认 → 正式应用工具校验文件哈希、归属和列契约 → 写入成功后再标记已应用 → 回读结果。

实现结果：`CaseBlindspotPanel` 改为「预览写回 → 确认写入文件」；`/__tb_caseblindspot/draft|apply` 与 `lantern_case_blindspot_*` 固定文件哈希、草稿 revision、插入位置和逐项回执，写入成功后才更新 `added`。

验收至少包括：

- 未确认、取消、失败均不修改原文件，也不提前标记已补全。
- 仅修改选中项，保留其它行的执行结果、缺陷链接和稳定标识；新增/变更用例按现有资产契约处理验证状态。
- 按真实表头、RO/US/TP 与归属分组写入，未知引用和无法归组的内容明确提示。
- 确认后文件变更则拒绝旧稿；重复应用不重复插行。
- 成功回执包括新增/修改数量、真实文件路径和未处理项，不能以“跳转成功”代替“写入成功”。

证据：`cli/mcp-server.mjs:2647`、`src/components/islands/CaseBlindspotPanel.tsx:85`、`src/components/islands/CaseReviewDrawer.tsx:972`、`lh-plugins/lh-case-review.mjs:701` 与 `:772`。

### W2（已完成）：测试报告材料与结果审阅

**为什么适合窗口：** 重点不是选择报告类型，而是让用户核实“这份报告到底用了哪些环境、版本与证据”。功能、接口和性能报告应保持各自的材料与口径。

原缺口：`TestReportsLibrary` 原仅提供三类归档和会话编辑；本轮已补正式报告整理服务。

实现结果：`TestReportsLibrary` 增加「整理报告」抽屉；`/__tb_test_report_review/context|draft|apply` 与 `lantern_test_report_*` 读取真实用例、测试统计和执行统计，校验声明数字、`sourceRevision` 与目标报告哈希，确认后原子写入。

建议流程：选报告类型、版本/环境与模板 → 选择真实来源 → 读取可复核的统计与缺口 → Codex 写草稿 → 页面预览章节差异和证据 → 用户确认 → 正式保存/归档 → 返回路径与来源清单。

验收至少包括：

- 指标能够追溯到真实执行结果、统计记录或用户上传的材料；不同环境不能随意合并。
- 区分未取得数据、未执行、失败、阻塞与实际为零，不能凭空给出通过率。
- 对已有报告修改必须提供文件哈希与差异；新报告不覆盖同名文件。
- 性能报告只能整理已有压测与监控证据；**支持性能用例/报告，不代表实现了性能压测执行插件。**
- 最终是否发布的判断仍由人做，不通过报告窗口自动放行。

工作量比 W1 更大：需要先定义统一材料引用、统计口径及服务端验证/归档，不能只把文件库装进一个弹窗。已有用例、验收、统计与自动化 MCP 的读取能力可以复用，不应重做。

证据：`src/components/islands/TestReportsLibrary.tsx:391`、`src/lib/test-reports.ts:19` 与 `:44`、`src/lib/doc-roots.ts:38`。

## 8. 共用交互约束与实施顺序

建议先让 W1 走通，再做 W2；两个真实场景都完成后再抽出共用状态管理，不先建设一个包含全部插件的新平台。

复用当前用例窗口的状态模式，但不要直接把用例专用字段套到所有模块：

1. **固定上下文。** 请求记录空间、业务对象、来源 revision/文件哈希、输入范围和有效期；确认、回读、执行时均复核，切换活动空间不能把结果应用到另一空间。
2. **明确状态。** 区分待选择、已确认、已取消、已过期、应用中、已应用、应用失败；“配置已确认”不等于“资产已写入”。
3. **确认只做一件事。** 按钮写清“确认配置并返回”或“应用选中修改”。页面和 Codex 不能各执行一次，也不能靠用户关闭窗口推断同意。
4. **回读后继续。** 返回稳定交互 ID，Codex 读取确认数据后才执行后续工具。浏览器页面确认不会天然唤醒聊天：当前实现仍需用户回聊或客户端显式等待/查询，不能承诺无需宿主支持的自动续跑。
5. **可见结果。** 页面显示加载、失败原因、过期重建、已确认/已应用、真实资产链接；暂停和关闭保留可恢复草稿，不假报成功。
6. **正式持久化。** 校验引用与格式、文件哈希/revision、去重与幂等；应用成功后回写状态，再提供回执。保留原模块的权限与数据隔离，不靠直接 JSON 改写跳过规则。
7. **复用控件。** 使用既有页面/抽屉、单选与多选、焦点与键盘支持、窄屏/深色主题；不会要求所有普通操作都先开窗口。
8. **客户端可替换。** 原生 MCP 表单只作为可选入口，浏览器链接与交互 ID 可跨 MCP 客户端使用；发布包必须带上页面和服务端路由，不能要求每台机器改审批策略。

参照实现：`lh-plugins/case-setup-window.mjs`、`src/components/islands/CaseSetupWindow.tsx`、`src/pages/cases/configure.astro`、`cli/mcp-server.mjs` 的 browser/setupId 分支。目前参照实现的状态是 pending/confirmed/cancelled，30 分钟有效、服务进程内保存；完整的应用状态属于后续业务服务，不能说现已全部具备。

建议验收顺序：

- 第一阶段：W1 正式写回事务与 MCP；复用盲区/修订页面审阅；验证不提前标记、基线变动拒绝和重复应用。
- 第二阶段：W2 真实材料契约与报告归档；再做证据选择/章节差异窗口，验证统计口径和来源缺失。
- 按需阶段：只有实际工作量证明聊天确认不够时才做 W3–W7；简单操作直接补 MCP。
